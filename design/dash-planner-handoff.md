# Handoff: the dash path planner rework (grid and precomputed routes)

Written 2026-11-06 for another AI model (or person) who takes this feature over. It is self-contained: read it top to bottom, then `design/dash-planner-grid.md` (the design and the numbers) and the files named in section 4. **Nothing in the robot code has been changed for this feature yet.** What exists is a design, one analysis script, and measurements.

## 1. The project in one paragraph
FTC team 8533 (CSPA Miners), game BIOBUZZ (2026-27). The robot ("ROBOT_1", a mecanum chassis with a Pinpoint odometry computer) launches pollen into the two cells of a central HIVE, gathers pollen from FLOWERS and a GARDEN, and parks in a loading zone. Code: Java, FTC SDK 12.0, repository `C:\Users\mkbla\Documents\FTC\2026-BIOBUZZ-PROD` (GitHub `Miners-8533/2026-2027-competition`), package `org.firstinspires.ftc.teamcode`, working branch `integration` (pushed through commit `7089d16`; `main` holds an earlier merge only; nothing since 2026-11-05 evening has been merged to `main`). The user is the team's programmer and decides what is built; windows machine, both a bash and a PowerShell tool exist.

## 2. The feature
**Hive Dash**: the driver holds D-pad left or right in `TeleOp - Competition` and the robot drives itself to the launch spot of a hive cell, turns onto the cell (the "target lock") and launches. **Park Dash**: D-pad up or down drives to a park corner of the loading zone and holds there. Both use one planner, `HiveRoute`, today.

**The user's idea (their words, condensed):** have a grid of starting points. When a hive-cell dash is selected an algorithm picks ONE of them so the robot is moving in the general direction of the final target. Once the start grid point is chosen there is a set of precomputed optimal paths to the desired location, so there is no collision calculation on the fly; with a good set of start points collisions are avoided without computing them live, and as much simulation and computation as wanted goes into the preselected routes. The routes overlap a lot, so they need not all be unique: a tree data structure may help. Computing them needs a good collision simulation and a simulation of the robot's motion dynamics, which can be derived from the many logs. A hive cell may have several launch spots; to start, one each, the current preferred spots.

**Decisions the user made (2026-11-06):**
1. The robot DRIVES TO the chosen grid point first, then follows the precomputed tree (so the precomputed math is never disturbed by an arbitrary start).
2. The WHOLE FIELD is covered; starts that already count as collided (inside a flower stand or a hive support foot) need no handling.
3. The same approach serves the Hive Dash AND the Park Dash.
4. The tables are generated by a ONE-COMMAND tool on a PC and checked in as generated source.
5. Acceptance to start: replay the logged dashes in the simulation and require it to reproduce them; later, when logs exist of the real code running these tables, verify further.

## 3. Why (the evidence behind the rework)
From the TeleOp logs of 2026-11-06 (`robot-logs/2026-11-06/000512_teleop.log` and `004300_teleop.log`):
- Two dashes from the Blue Wall side to the audience cell went `(-65, 50) -> via helper (36, 40) -> (55.4, 7.5)`. The robot passed the helper point at about 70 in/s, the next leg is a 38 in diagonal, and momentum carried it to (59, 29), 17 in off the leg line, into the audience flower stand (its speed fell from 42 to 8 in/s there). The planner models straight legs and nothing about speed or momentum.
- Arrivals at the launch spot at 20 to 55 in/s coasted 2 to 8 in past the spot (toward the flower).
- The audience launch spot is only 6.8 in from the flower stand, so the planner's flower clearance cannot exceed 3 in (4 in made 812 of 1500 trips to a spot unreachable) because the last box of a leg is a circle of radius 12 in.
- Fixes already made and committed (not yet seen on the robot): approach power cap and corner slowdown in `HiveDash`, 3 in flower clearance in `HiveRoute`, launch spots moved to x = +-55.4 (8 in from the wall). These stay until the new system replaces them.

## 4. The current code (the system being replaced)
All under `TeamCode/src/main/java/org/firstinspires/ftc/teamcode/` unless stated.
- `drive/HiveRoute.java` (PURE Java, no SDK): keep-outs, `plan(startX, startY, startHeading, goalX, goalY, Params)`, swept-box leg checks, a search over hand-placed points (helper corners (+-36, +-40), lane gates (+-34, 0), at most 3 via points). Compiles on a PC.
- `drive/HiveDash.java`: the state machine and follower (`update(Input) -> Output`): drives each leg with the heading aligned to travel (front or rear leading), `MAX_POWER` 0.85, `TURN_MAX` 0.5, the approach cap, the corner slowdown, the target lock handoff 20 in (32 in outside the hive) from the spot, the launch when aligned and still. Pure logic apart from a Dashboard overlay and `RunLog` calls.
- `drive/ParkDash.java`: the same for the park corners, plus a hold at the corner.
- `drive/AutoLaunch.java`: the launch spot constants (`BLUE_REAR (-55.4, 15.25)`, `BLUE_AUDIENCE (55.4, 7.5)`, `RED_AUDIENCE (55.4, -15.25)`, `RED_REAR (-55.4, -7.5)`).
- `drive/TargetLock.java`: the aim law that turns the robot onto a cell; `drive/MecanumDrive.java`: `setDrivePowers(PoseVelocity2d)` mixes `lf = x - y - w`, `lb = x + y - w`, `rb = x - y + w`, `rf = x + y + w` and divides by `max(1, max |wheel|)`; a 0.01 write deadband; **y is positive to the robot's left**, w is counterclockwise positive.
- `opmodes/TeleOpCompetition.java`: the glue. Each loop it builds a `HiveDash.Input` (pose, measured velocity, requested cell, blocked reasons, counter flags, lock aligned, launch busy), calls `hiveDash.update`, then applies the `Output`: `translation` -> `robotForward/robotLeft` (robot frame powers), `turnActive` -> `cmdTurn = dash.turn`, `lockWanted` -> the target lock computes the turn, `launchNow` -> a salvo; `HoldPosition` may override; finally `drive.setDrivePowers(new PoseVelocity2d(new Vector2d(robotForward, robotLeft), cmdTurn))`. The loop runs about every 30 ms.
- PC checks (compile only `HiveRoute` plus a tool): `tools/hive/HiveRouteCheck.java`, `tools/hive/DuoPathCheck.java`, run with `tools/hive/run-check.cmd` or the javac/java lines inside it.
- Design notes: `design/hive-dash.md`, `design/park-dash.md`, `design/dash-planner-grid.md` (this feature), `design/idea-queue.md` item 8.

## 6. The logs (the data)
- Files: `robot-logs/YYYY-MM-DD/HHMMSS_teleop.log` and `_auto.log` (the hub's logs pulled with `python tools/logs/pull_logs.py`; a PC copy of every run since 2026-11-01). Format and every event: `design/run-logs.md`.
- Rows: `E,<t>,<text>` events and `S,<t>,...` samples every 100 ms (a row on every loop around a launch). TeleOp S columns (index after splitting on commas, `S` = 0): 1 t, 2 loop ms, 3 worst loop ms, **4 battery volts**, **5 x, 6 y, 7 heading (deg)**, 8 stick up, 9 stick right, **10 cmd_fwd, 11 cmd_left, 12 cmd_turn** (the robot-frame command sent to the drive, before `setDrivePowers` normalizes it), 13 drive mode, 14 lock error (deg), then the mechanisms' columns. The auto logs have no command columns.
- Dash events: `HIVE DASH start (CELL): from (x, y, deg) to the launch spot (x, y), via (...)`, `HIVE DASH leg i of n ...`, `HIVE DASH via point (...) reached at (...)`, `HIVE DASH arrived after s at (x, y, deg), d in from the launch spot`, `HIVE DASH launching ...`, `HIVE DASH finished ...`, `HIVE DASH cancelled (...)`, `HIVE DASH sample: t, pose, speed, travel angle, leg` (every 0.25 s), and the `PARK DASH ...` equivalents.
- The dash logs that matter: 2026-11-05 `205206`, `212455`; 2026-11-06 `000512`, `004300`, `011331`, `015817` (TeleOp). About 134 dash segments with commands exist. The 2026-11-06 `011331` run lost its expansion hub to a low battery partway (ignore its flywheel and the end of the run).
- Pose source: the Pinpoint (about 0.1 in noise, a small heading-dependent y shift is known and ignored).

## 7. What has been done (Phase 1a, the drive model)
- `tools/dash/identify_drive.py` (new, **uncommitted**): fits a per-axis model of the drive from the logs. Run `python -I tools/dash/identify_drive.py` (all TeleOp driving rows) or `... dash` (dash rows only); it prints the parameters and writes `drive_model_all.npy` / `drive_model_dash.npy` beside it (ignored by git via `.gitignore`). Needs numpy and scipy.
- Model: command -> wheel powers -> normalize exactly as `MecanumDrive` does -> per axis a first-order lag towards `gain * (volts / 12) * sign(c) * max(0, |c| - deadzone)` with separate time constants for speeding up and slowing down; the body velocity integrates into a pose. Objective: pose error at every later row of 8-row (0.7 s) windows, starting from the measured velocity.
- Result (all driving / dashes only): forward gain 86 / 99 in/s per unit, strafe 63 / 52, turn 6.3 / 6.7 rad/s; time constants 0.17 to 0.38 s up, 0.12 to 0.22 s down; the steady speed is about 38 in/s at 0.5 power and 64 in/s at 0.85. Pose error within a window 2.1 to 2.6 rms (8.5 to 12 doing nothing); after 0.46 s a median 1.5 to 1.8 in; after 0.81 s a median 2.8 to 3.7 in (90th percentile 7.8 to 8.4 in); heading error a median 5 to 6 deg after 0.81 s and up to 19 to 30 deg (90th percentile) in hard turns. A plain per-step fit bottomed out at 0.74 in per 100 ms whatever nonlinearity was added: the floor is the data (the logged command is a 100 ms snapshot of a command that changes every 30 ms).

- Commit state: the design doc (`2dd3541`), the script, the `.gitignore` line, the second-pass section and this handoff (`77122e2`) are committed. Standing rule from the user: commit and push ONLY when asked.

**Phase 1d: replay and the acceptance gate.** For each logged dash start the simulation at the logged start pose and heading with the same cell and battery voltage, run the real dash, and compare: the simulated track against the logged one (suggested: median position difference under 4 in along the whole dash and the arrival point within 3 in), the corner swing at (36, 40) reproduced within about 5 in, the two audience-flower contacts detected, and the arrival coast (2 to 8 in) reproduced. **Phase 2:** measure what a grid would add over the current planner in the simulation (time per dash, clearance). **Phase 3:** the generator tool (a Dijkstra-style shortest-path tree per goal over a grid of positions and a few headings, cost = simulated time, clearance constraint with an allowance for the tracking error, red generated from blue by the 180 degree rotation), the generated Java table, the runtime (pick the node minimizing the distance to it plus its cost-to-go among nodes reachable by a straight clear drive; drive to it; follow the route with its speed profile; a deviation guard that aborts or re-snaps when more than N in off the route), the Park Dash on the same tables, tests on the PC (`tools/hive` style) and a robot test plan row in `design/integration-plan.md`.
